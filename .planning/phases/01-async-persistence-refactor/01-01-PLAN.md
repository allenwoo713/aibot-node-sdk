## Current Implementation Notes

`src/memory.ts` currently:
- Imports `fs` (sync API)
- Calls `fs.existsSync`, `fs.readFileSync`, `fs.writeFileSync`
- Constructor calls `this.load()` synchronously
- `save()` is synchronous and called directly from `append`, `clear`, `clearAll`
- Errors are silently swallowed with empty catch blocks

`BotConfig` (from `src/config/index.ts`) currently does NOT include a `logger` field, but `src/types/common.ts` defines the `Logger` interface. The `ConversationStore` constructor currently uses `Pick<BotConfig, 'conversationTtlMs' | 'maxConversations' | 'maxHistoryMessages' | 'persistencePath'>`.

## Target Design

1. **Constructor stays sync** but removes the immediate `load()` call.
2. **Lazy init**: an `initialized` boolean + `private async init()` that runs `load()` once. Guard `get`, `append`, `clear`, `clearAll`, `buildMessages` with `await this.init()`.
3. **Async I/O**: Use `fs/promises` (`access`, `readFile`, `writeFile`, `rename`). Replace `existsSync` with `access(path).then(() => true).catch(() => false)`.
4. **Write queue**: A private `saveQueue: Promise<void> = Promise.resolve()` field. All disk writes are chained: `this.saveQueue = this.saveQueue.then(() => this.doSave()).catch(...)`.
5. **Atomic writes (POSIX)**: Write to a temp file next to the target (`${persistencePath}.tmp`), then `fs.rename()` it to the target. On Windows, skip rename and write directly because the queue already serializes.
6. **Backward-compatible signatures**:
   - `get(conversationId: string): HistoryMessage[]` — stays sync (reads from in-memory Map)
   - `buildMessages(...)` — stays sync (calls `get`)
   - `append(conversationId, message): Promise<void>` — now returns Promise
   - `clear(conversationId): Promise<void>` — now returns Promise
   - `clearAll(): Promise<void>` — now returns Promise
   - `save(): Promise<void>` — now returns Promise
7. **Logger integration**: Add `logger?: Logger` to the constructor options. On I/O errors, call `this.logger?.warn('Persistence error: ...', error)` instead of swallowing silently.
8. **Corrupt-state recovery**: In `load()`, catch JSON parse errors and invalid records, log a warning, and start fresh (same behavior as before).

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-01 | Tampering | `load()` parsing persistence file | mitigate | Wrap `JSON.parse` and file read in try/catch; on failure discard state and log warning. Preserve existing corrupt-state recovery behavior. |
| T-01-02 | Information Disclosure | logger warnings include file paths or error details | accept | Logger interface is under caller control; file path disclosure is low severity for a local JSON store. No PII is persisted. |
| T-01-03 | Denial of Service | malformed persistence file causes repeated load failures on every init | accept | Same behavior as existing sync implementation; scope is local process only. |
| T-01-04 | Elevation / Race Condition | concurrent writes to same JSON file | mitigate | Serialize all disk writes through an in-memory Promise chain (`saveQueue`). Only one `writeFile`/`rename` runs at a time. |
| T-01-05 | Tampering | partial write leaves corrupt JSON on crash | mitigate | On POSIX platforms write to `.tmp` then `fs.rename()` to target for atomic replacement. |
</threat_model>
